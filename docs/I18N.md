# i18n status: Applies — gettext seam merged; release gate partially met

Reason: The gettext extraction seam, EN/ES catalogs, and locale-selection CLI
boundary are merged (this document's own history is the record). What remains
before the first public tagged release is a qualified Spanish-language
terminology review of the drafted catalog, and translating the rule engine's
per-finding message and remediation text, which this pass did not reach. This
is a known pre-release gap, not an N/A control.

## Current boundary

- Command names, machine-readable JSON field names, rule IDs, and source
  citations remain stable, untranslated identifiers. Report-schema tests
  (`tests/test_reporting_i18n.py`) prove that changing locale changes
  human-readable prose but never these identifiers.
- Console messages, HTML report prose, finding summaries, remediation guidance,
  CLI help, and user-visible errors are localizable content.
- Filing-package text is user data. It must never be sent to a translation
  service or added to a message catalog.
- No language may imply that an advisory finding is a legal determination.

The opt-in `ai` commands ([ADR 0002](adr/0002-ai-at-the-edges.md)) add
user-facing prose. Every such string lives in `ceqa_preflight.ai.messages`,
one function per string so the gettext extractor sees a literal at its `_()`
call site; `ai/cli.py` calls those functions instead of formatting a bare
constant. None of it may imply that an advisory result is a legal
determination. The Spanish phrasings in the refusal suite
(`evals/refusal/cases.json`) were written by the maintainer and, like the
`es` report catalog below, await the qualified review named in the release
gate.

## What is implemented

- `ceqa_preflight.i18n`: a small module backed by Python's stdlib `gettext`.
  `_()`/`gettext_()` and `ngettext_()` translate under a process-wide active
  locale set once, explicitly, at the CLI boundary — never inferred from the
  OS locale, network, IP, or document content. An unsupported-but-valid BCP 47
  tag (e.g. `fr`) falls back to English deterministically rather than erroring;
  a malformed tag is rejected.
- `ceqa-preflight --locale <tag>`, falling back to the `CEQA_PREFLIGHT_LOCALE`
  environment variable, then English. The root Typer callback resolves and
  sets the locale before any subcommand (including `ai`, `rules`, `pilot`)
  runs.
- Every localizable string is a plain English literal used as its own msgid,
  translated at render time (never at import time), so a batch `check` run —
  or a test — can render more than one locale in a single process.
- Committed catalogs: `src/ceqa_preflight/locales/ceqa_preflight.pot` (the
  extraction template), and `en`/`es` `.po` sources with compiled `.mo`
  catalogs, shipped inside the wheel (verified by building the wheel and
  installing it into a clean virtualenv with no source tree access). `en.po`
  is the identity translation — English is its own source language, so no
  interpretation is introduced. `es.po` is maintainer-drafted, matching the
  refusal-suite precedent above, and **awaits the qualified review in the
  release gate**.
- `make i18n-extract` / `make i18n-update` / `make i18n-compile` (Babel-backed,
  dev-only) and `make i18n-check`, wired into `make verify`
  (`scripts/check_i18n.py`): POT-freshness against the current source tree,
  EN/ES key parity, placeholder parity (`{name}` and Jinja's `%(name)s`
  trans-block form), BCP 47 validity of each shipped locale code, and that
  every committed `.mo` matches its `.po`.
- Coverage of the seam: `reporting.py` (console, checklist, and HTML
  renderers, including the Jinja2 `jinja2.ext.i18n`-driven template and its
  `<html lang>` attribute), the report's disclaimer (`checker.DISCLAIMER`),
  every `ai` command's console prose (`ai/messages.py` via `ai/cli.py`), and
  the top-level `cli.py`/`ai/cli.py` errors, confirmations, and `--format`
  validation messages.
- `tests/test_i18n.py` (locale resolution, BCP 47 validation, fallback,
  translation) and `tests/test_reporting_i18n.py` (EN/ES/fallback rendering of
  a full report across all four renderers, proving rule IDs, finding status
  values, JSON keys, and citation URLs never change with locale) plus
  `tests/test_cli.py::TestLocaleSelection` (the `--locale` option, the env
  var, precedence between them, and the deterministic fallback, exercised
  through the real CLI).

## What is not yet implemented

- **Rule engine message text**: the finding `message` and `remediation`
  strings generated by `rules/common.py`, `rules/filing.py`, `rules/nod.py`,
  and `rules/noe.py`, and the rule catalog's `title`/source metadata
  (`rule_catalog.py`), are not wrapped in `_()`. This is by far the largest
  remaining body of user-facing prose (100+ distinct strings, many
  interpolating package-specific facts) and translating it correctly needs
  the same qualified CEQA review the release gate already requires for
  terminology — it was intentionally left for a follow-up pass rather than
  translated without that review. `pilot.py`'s summary reasons and
  `synth.py`/`scaffold.py`'s confirmation text are the same kind of gap, at
  smaller scale.
- Typer/Click's own auto-generated `--help` and usage chrome (option lists,
  error framing like "Error: Invalid value for ...") is not localized; only
  the command help strings and this project's own echoed messages are.

## Implementation entry point

Historical note: this section originally specified the module, wrapping
convention, and `make verify` obligations before they existed. They now do,
as described above; kept here as the record of what was specified and
verifiable against what shipped.

Introduce a small `ceqa_preflight.i18n` module backed by Python gettext. Wrap
localizable source strings in `_()` and plural forms in `ngettext()`, extract a
committed POT file, and ship reviewed `en` and `es` catalogs. Locale selection
must be explicit at the CLI boundary, with deterministic English fallback; it
must not use network, IP, or document-content inference.

`make verify` must then enforce catalog compilation, EN/ES key and placeholder
parity, BCP 47 locale validity, and extraction freshness. Report-schema tests
must prove that locale selection changes human-readable prose but never
machine-readable keys, rule IDs, finding status values, or citations.

## Release gate

The first public tagged release is blocked until:

1. ~~the gettext entry point and extraction configuration are merged~~ — done.
2. ~~English and Spanish catalogs compile with complete key and placeholder
   parity~~ — done for the strings this pass reached (see "What is not yet
   implemented" above for the rule-engine gap still open).
3. a qualified Spanish-language reviewer approves CEQA terminology and the
   advisory/non-legal framing — **open**; `es.po` is maintainer-drafted only.
4. ~~console and HTML report tests cover English, Spanish, and deterministic
   fallback~~ — done for the report renderers (`tests/test_reporting_i18n.py`,
   `tests/test_cli.py::TestLocaleSelection`).
5. the central applicability registry marks CEQA Preflight as I18N
   `applies` — this document already declares `Applies` at the top; whether
   the portfolio-level registry outside this repository reflects that is for
   its owner to confirm.
