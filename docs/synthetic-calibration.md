# Synthetic calibration: method and record

`ceqa-preflight pilot calibrate` measures the built-in rules against the
synthetic generator's seeded defects. The record it produces lives at
[`evals/synthetic-calibration.json`](../evals/synthetic-calibration.json) and is
regenerated by:

```
ceqa-preflight pilot calibrate --out evals/synthetic-calibration.json
```

`--check` compares a fresh measurement against the committed file and exits
non-zero on any difference, so the published record cannot detach from the
ruleset it describes.

## What this measures

For each seedable defect, whether the rule that owns it reached `warning` or
`failure` on a package containing it — a **detection rate against the
generator's notion of a defect**. And, for every rule that ran, how often it
fired on a package that seeded nothing for it — an **unseeded-finding rate**.

Every rate carries a 95% Wilson interval. Four detections out of four is
published as its interval, not as `100%`: the corpus is small, and a bare point
estimate invites reading a sample of four as certainty.

## What this does not measure

**It is not a false-positive rate**, and the record carries
`false_positive_rate: null` with a written reason rather than a number. A
false-positive rate is a rate against *real filings*, and it needs qualified
CEQA reviewers labelling real findings — that is issue #81. A finding on a
synthetic package that the generator did not seed is not thereby wrong; it may
be a correct observation about the generator's own output. Counting those as
false positives would publish a number with no referent.

**It is not a reviewer-time figure**, and `reviewer_seconds_median` is likewise
`null` with its reason. Nobody reviewed these packages. The wall clock of an
automated run is a property of the machine that ran it, so it is deliberately
absent from the record rather than offered as a stand-in — the record has no
field ending in `_seconds` at all, and a test enforces that.

## Why the sample is small, and why it is not padded

`synth` is deterministic: one defect and one filing type produce one package,
byte for byte, every time. Generating it a hundred times would raise the
denominator without adding a single independent observation. So the corpus is
exactly the distinct packages available — a control, each defect alone, and
every defect at once, for each of NOE and NOD: **22 packages, four seeded
observations per defect.** The intervals show how little that is.

## What the corpus does not reach

The record lists `unexercised_rules` rather than omitting them, because a record
naming only the rules it exercised cannot be told apart from one that exercised
everything. As committed, **18 of the 26 built-in rules are unexercised, and
that includes every filing-specific rule** — `NOE-001`…`NOE-M003` and
`NOD-001`…`NOD-M003`, which are exactly the rules the permissioned pilot exists
to activate. The generator seeds no filing-specific defect, so this measurement
says nothing about them.

Two further absences are kept from reading as clean results:

- A rule that did not run has `rate: null`, not `0.0`. A withdrawn or unselected
  rule fires zero times by construction and has not earned a clean record.
- A rule whose only observed outcome is `manual` cannot reach `warning` or
  `failure` at all, so its zero is structural. `statuses_observed` records what
  it actually produced, so the two cannot be confused.

## Degraded reads

PDF inspection runs in a spawned worker with a wall-clock timeout. If it times
out or returns nothing, the rule that needed those facts routes to a human
instead of firing. That is counted as `undetermined`, never as a miss: a rule
that could not read the file has not failed to detect anything, and folding the
two together would publish a loaded machine as a weaker ruleset.

`undetermined_reads` is zero in any record worth publishing. This is not
hypothetical, and it is not only a loaded-laptop problem: it reproduces on all
three CI runners while the same command over the same corpus is clean on a
developer machine. Roughly one PDF inspection in eighty on a two-core runner
comes back with the worker having never answered.

So an incomplete read is **taken again**, up to three attempts per package,
before it is recorded. That is not a relaxed assertion. The corpus is
deterministic, so a rule that could not read a file it read a moment ago is
reporting a fact about the machine, and `undetermined` is the tool saying "ask
again", not "no". A read that stays incomplete after every attempt is still
counted, `undetermined_reads == 0` is still required, and the failure names which
defect and rule went undetermined rather than sending the reader back to re-run
the corpus.

Every retry is announced on stderr. A run that needs one every time is a broken
environment, and hiding that would trade one silent wrong number for another.
The retry count is deliberately **not** in the record, for the same reason wall
clock is not: it is a property of the machine that ran the measurement, not of
the ruleset the record describes.

## Relationship to `pilot summarize`

Different inputs, different questions. `pilot summarize` aggregates controlled
labels a qualified reviewer produced, and answers the precision and agreement
questions. This command needs no reviewer and answers only what the machine can
establish alone. Neither substitutes for the other, and the synthetic figure
must be labelled as the synthetic figure wherever it appears.
